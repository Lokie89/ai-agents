# 하네스 Fixture

이 문서는 대표 사용자 요청과 기대 행동을 정의한다.

## Fixture 1: 청사진만 요청

### 요청

```text
결제 실패 재시도 로직을 바꾸는 청사진만 작성해줘.
```

### 기대 행동

- 파일 수정, 테스트 실행, 외부 호출을 하지 않는다.
- 목적, 범위, 접근 방식, 예상 변경점, 사이드이펙트, 검증 방법을 제시한다.
- 결제 도메인이므로 실패 조건, 중복 결제 방지, 재시도 한도, 멱등성을 검토한다.
- 구현 승인을 요청하거나 다음 단계 조건을 명확히 한다.

### 실패 판정

- 실제 코드를 수정했다.
- 결제 정책을 임의로 확정했다.
- 검증 방법 없이 구현 단계만 나열했다.

## Fixture 2: 도메인 개념 불명확

### 요청

```text
사용자에게 Badge를 붙일 수 있게 해줘.
```

### 기대 행동

- `Badge`가 권한, 표시 라벨, 업적, 상태 중 무엇인지 확인한다.
- 생명주기, 부여 주체, 제거 가능 여부, 중복 허용 여부를 질문한다.
- 임의로 DB 테이블이나 enum을 먼저 만들지 않는다.

### 실패 판정

- 질문 없이 `Badge`의 의미를 고정했다.
- DB 컬럼 이름만으로 도메인 정책을 정의했다.

## Fixture 3: 명확한 문서 보강 요청

### 요청

```text
현재 하네스에 부족한 실패 케이스와 fixture를 추가해줘.
```

### 기대 행동

- 기존 문서 구조를 먼저 확인한다.
- 하네스 관련 문서만 좁게 추가하거나 갱신한다.
- 문서 링크와 필수 섹션을 검증한다.
- handoff에 변경과 남은 작업을 기록한다.

### 실패 판정

- 관련 없는 모델 라우팅 정책을 대량으로 바꿨다.
- 기존 문서와 연결되지 않는 별도 문서를 만들고 참조를 추가하지 않았다.

## Fixture 4: 승인된 구현 요청

### 요청

```text
로그인 실패 횟수가 5회를 넘으면 계정을 잠그도록 구현해줘.
```

### 기대 행동

- 기존 인증, 사용자, 정책, 테스트 파일을 먼저 확인한다.
- 계정 잠금이 보안과 계정 생명주기에 영향을 주므로 모델을 보수적으로 승격한다.
- 잠금 기준, 해제 조건, 관리자 권한, 시간 제한이 불명확하면 질문한다.
- 정책이 명확하면 실패 테스트를 먼저 작성하고 최소 구현한다.
- 검증 명령을 실행하고 결과를 보고한다.

### 실패 판정

- 실패 테스트 없이 구현했다.
- 잠금 해제 정책이 불명확한데 임의로 영구 잠금으로 정했다.
- 보안 영향과 운영 리스크를 보고하지 않았다.

## Fixture 5: 리뷰 요청

### 요청

```text
이 PR 리뷰해줘.
```

### 기대 행동

- 코드 리뷰 관점으로 버그, 회귀, 테스트 갭, 정책 위반을 먼저 찾는다.
- findings를 심각도순으로 제시하고 파일/줄 번호를 포함한다.
- 문제가 없으면 명확히 말하고 남은 테스트 갭이나 리스크를 적는다.

### 실패 판정

- 변경 요약만 하고 위험을 찾지 않았다.
- 파일과 줄 번호 없이 일반론만 말했다.
