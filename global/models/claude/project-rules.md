# 프로젝트 규칙

이 문서는 Claude가 새 프로젝트를 만들거나 기존 프로젝트에 처음 들어갈 때 적용하는 글로벌 기준이다.

로컬 프로젝트 정책은 실제 프로젝트 안에서 `local/<project-name>/` 문서로 만든다. 이 문서는 로컬 문서를 지금 채우기 위한 것이 아니라, 로컬 규칙이 없거나 부족할 때 어떤 대화와 하네스를 생성해야 하는지 정의한다. `local/`은 [Codex](../codex/project-rules.md) 등 다른 모델과 공유될 수 있으므로 산출물은 모델이 아니라 프로젝트 기준으로 둔다.

## 프로젝트 진입 기준

- 먼저 사용자 요청이 새 프로젝트 생성인지, 기존 프로젝트 수정인지, 단순 분석인지 분류한다.
- `Glob`/`Read`로 저장소 구조, 실행 파일, 설정 파일, lockfile, 테스트 파일, README를 확인한다.
- 해당 프로젝트의 로컬 문서가 있는지 확인한다.
- 로컬 문서가 있으면 글로벌 규칙보다 로컬 정책을 우선한다.
- 로컬 문서가 없거나 비어 있으면 구현 전에 필요한 범위의 로컬 하네스 대화를 생성한다.
- 단순 분석이나 코드 변경이 없는 질의는 로컬 하네스 생성을 강제하지 않는다.

## 로컬 하네스가 필요한 경우

아래 중 하나라도 해당하면 `local/<project-name>/` 하네스가 필요하다.

- 새 프로젝트를 생성한다.
- 도메인 개념, 엔티티, 상태, 권한, 생명주기, 불변 조건을 추가한다.
- 실행, 테스트, 빌드, 배포 방식이 프로젝트마다 달라진다.
- 환경변수, 비밀값, 외부 서비스, 데이터 저장소를 사용한다.
- 장기 작업이거나 다음 세션 인계가 필요하다.
- 글로벌 규칙과 다른 예외가 필요하다.

## 로컬 하네스 대화

로컬 규칙이 없거나 부족하면 한 번에 모든 것을 묻지 않고, `AskUserQuestion`으로 구현에 필요한 최소 질문부터 제시한다.

### 필수 질문

- 프로젝트 이름과 목적은 무엇인가?
- 새 프로젝트인가, 기존 프로젝트인가?
- 주요 사용자와 핵심 사용 흐름은 무엇인가?
- 사용할 기술 스택, 런타임, 패키지 관리자는 무엇인가?
- 실행, 테스트, 빌드 명령은 무엇인가?
- 도메인 개념 중 아직 확정되지 않은 용어가 있는가?
- 환경변수, 비밀값, 외부 서비스, 데이터 저장소가 필요한가?
- 배포 또는 운영 영향이 있는가?

### 조건부 질문

- 인증, 권한, 개인정보, 결제, 데이터 삭제가 관련되는가?
- 마이그레이션이나 되돌리기 어려운 변경이 있는가?
- 실패해야 하는 입력, 금지 상태, 허용되면 안 되는 상태 전이는 무엇인가?
- UI가 있다면 주요 화면, 반응형 기준, 접근성 요구가 있는가?
- API가 있다면 소비자, 인증 방식, 오류 응답 기준은 무엇인가?

## 로컬 하네스 산출물

필요한 답을 얻으면 아래 파일을 생성하거나 갱신한다.

```text
local/<project-name>/
  goal.md
  context-map.md
  domain-policy.md
  tools.md
  validation.md
  handoff-log.md
```

새 로컬 문서는 `local/_template/`의 템플릿을 우선 사용한다. 템플릿이 없는 경우 아래 역할 표를 기준으로 최소 구조를 만든다.

각 파일의 역할은 아래와 같다.

| 파일 | 역할 |
| --- | --- |
| `goal.md` | 프로젝트 목표, 제외 범위, 완료 기준 |
| `context-map.md` | 코드, 문서, 데이터, 설정 위치 |
| `domain-policy.md` | 도메인 용어, 상태, 권한, 생명주기, 미결 질문 |
| `tools.md` | 프로젝트별 허용 도구, 금지 도구, 승인 필요한 명령 |
| `validation.md` | 실행, 테스트, 빌드, 린트, 배포 전 검증 |
| `handoff-log.md` | 변경, 검증, 남은 작업, 주의 사항 |

## 새 프로젝트 생성 기준

새 프로젝트를 만들 때는 최소한 아래 산출물을 남긴다.

- 실행 가능한 기본 애플리케이션 또는 라이브러리 구조
- README의 설치, 실행, 테스트 명령
- 필요한 경우 `.env.example` 또는 환경변수 문서
- 기본 테스트 또는 가장 가까운 검증 명령
- 로컬 하네스 문서
- 실패한 검증과 미실행 검증의 이유

## 새 프로젝트 기본 완료 체크리스트

- 첫 화면, CLI 도움말, API health check 중 프로젝트 유형에 맞는 진입점이 동작한다.
- 사용자가 요청한 핵심 흐름이 최소 1개 이상 동작한다.
- 오류 상태 또는 빈 상태가 하나 이상 정의되어 있다.
- README만 보고 설치, 실행, 검증을 재현할 수 있다.
- 외부 서비스가 필요한 경우 실제 비밀값 없이 `.env.example` 또는 환경변수 표가 있다.
- 테스트가 없으면 테스트를 만들지 못한 이유와 대체 검증 방법이 `validation.md`에 남아 있다.
- 다단계 생성 작업은 `TaskCreate`/`TaskUpdate`로 진행 상태를 추적했다.
- 생성된 파일과 실행하지 못한 검증이 최종 보고에 포함된다.

## 프로젝트 유형별 최소 기준

| 유형 | 최소 동작 | 최소 검증 |
| --- | --- | --- |
| 웹앱 | 첫 화면과 핵심 사용자 흐름 1개 | 빌드 또는 실행 확인, 가능하면 UI/단위 테스트 |
| API 서버 | health check와 핵심 엔드포인트 1개 | 서버 시작 확인, 엔드포인트 호출, 가능하면 API 테스트 |
| CLI | help 출력과 핵심 명령 1개 | 명령 실행 확인, 가능하면 단위 테스트 |
| 라이브러리 | 공개 API 예시 1개 | 단위 테스트 또는 샘플 실행 |
| 문서/하네스 | 링크와 필수 섹션 | 문서 검증 스크립트 또는 대체 검증 |

## 기존 프로젝트 수정 기준

기존 프로젝트에서는 새 구조보다 기존 패턴을 우선한다.

- 관련 파일과 테스트를 먼저 확인한다.
- lockfile과 패키지 관리자 기준을 따른다.
- 로컬 하네스가 없더라도 작은 단일 수정은 바로 진행할 수 있다.
- 도메인, 실행, 검증, 배포 방식이 불명확하면 로컬 하네스 대화를 먼저 생성한다.
- 기존 사용자 변경을 되돌리지 않는다. `Bash`/`PowerShell`로 `git status`를 먼저 확인한다.

## 로컬 하네스 생성 기준

- 사용자가 로컬 하네스 생성을 승인했거나, 새 프로젝트 생성처럼 로컬 하네스가 완료 기준에 포함되는 요청이면 필요한 파일을 만든다.
- 답이 없는 항목은 임의로 확정하지 않고 `미정` 또는 `결정되지 않은 질문`으로 남긴다.
- 로컬 정책이 글로벌 정책과 충돌하면 로컬 문서에 예외 이유를 기록한다.
- 비밀값은 문서에 쓰지 않고 이름, 목적, 필요 여부만 기록한다.
- 로컬 하네스 생성 후에는 `validation.md`에 실행 가능한 검증 명령과 미실행 사유 기록 기준을 둔다.

## 로컬 하네스 작성 품질 기준

- `goal.md`에는 프로젝트 목적, 주요 사용자, 핵심 흐름, 제외 범위, 완료 기준이 있다.
- `context-map.md`에는 README, 실행 진입점, 주요 소스, 테스트, 설정, 환경변수 위치가 있다.
- `domain-policy.md`에는 확정된 도메인 용어와 미정 용어가 분리되어 있다.
- `tools.md`에는 설치, 실행, 테스트, 빌드, 린트 명령과 승인 필요한 작업이 있다.
- `validation.md`에는 자동 검증, 수동 검증, 실패 보고 기준이 있다.
- `handoff-log.md`에는 최초 생성 기록과 남은 질문이 있다.
- 알 수 없는 항목은 비워두지 않고 `미정` 또는 `해당 없음`으로 표시한다.

## 완료 기준

- 프로젝트 유형이 분류됐다.
- 로컬 하네스 필요 여부가 판단됐다.
- 필요한 경우 로컬 하네스 대화가 생성됐다.
- 새 프로젝트라면 실행, 테스트, 문서, 환경변수 기준이 남았다.
- 기존 프로젝트라면 기존 패턴과 검증 방식이 확인됐다.
- 미정인 도메인 정책은 코드나 DB 구조로 확정되지 않았다.
